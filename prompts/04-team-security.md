# Stage 04: Team Security

## Objective
Make Team Memory safe for multiple people and agents: production OIDC authentication, scope-level roles over the hierarchy, PostgreSQL row-level security on all tenant data, an approval workflow, append-only audit logging, input defenses, and adversarial tests that try to break tenant isolation.

## Context
Team Memory is an open-source Go MCP service on PostgreSQL + pgvector for shared, versioned agent knowledge (see `proposal.md`). Trust levels: `unverified`, `cited`, `approved`; only maintainers approve. Key risks: one agent inventing a "convention" that other agents treat as fact; cross-tenant leakage (zero tolerated); stored memories acting as prompt injection; secrets saved into memory. Roles: reader, writer, maintainer. Authorization is enforced in both SQL (RLS) and Go.

## Work
1. **Authentication:** finalize the architecture selected in stage 03 as production code (the following facade details apply if that architecture was selected): the OAuth authorization-server layer, upstream OIDC login for any configured provider (client ID and secret read from Kubernetes Secrets at startup, hot-reloadable or documented restart), Team Memory token issuance and validation (issuer, audience/resource, expiry, signing-key rotation, JWKS), protected-resource and authorization-server metadata endpoints, and the personal access tokens from stage 01 (also used for CI/service accounts, with scopes). Fail closed: SSO enabled with missing or invalid configuration means not ready, never open. Auto-provision `principals` on first valid login per the stage 03 mapping, enforce per-org allowed email domains/issuers, implement the accepted CLI owner-bootstrap and authenticated SSO-linking contract documented in stage 03, preserving an existing solo owner; never assign ownership to an arbitrary first SSO login or link accounts solely by email. Role assignment is database-managed by default, with optional mapping from IdP group claims to project roles configured per org; SCIM is out of scope. SAML works only through a documented broker.
2. **Authorization in Go:** role checks per MCP tool (search/get/history/recent: reader; create/update: writer; supersede/approve: maintainer). Updating an `approved` memory must reset trust appropriately (define and document: e.g. a new revision of an approved memory becomes `unverified`/`cited` until re-approved) — state the rule in `docs/decisions/trust-rules.md`.
3. **Row-level security over the scope tree:** implement the stage 01 visibility rules in SQL (for example a `SECURITY DEFINER`-free, `STABLE` function or a precomputed closure table joined from `scope_members`, chosen for correctness and measured performance with deep trees and many members): own-scope reads need membership or a cascading ancestor grant; ancestor memories are readable by anyone who can read a descendant; descendants are never readable through an ancestor membership; writes, supersede, and approve require the matching role on the owning scope (or a cascading ancestor grant) and never on a merely inherited scope. Enable and `FORCE` RLS on every tenant-owned table, including `memory_revisions`, `memory_embeddings`, `approvals`, jobs data visible to users, and audit reads. Role-aware write policies. The application connects as a non-owner role without `BYPASSRLS`. Identity set via `SET LOCAL` inside every transaction (verify through the transaction helper that no query runs outside one). The worker uses a separate, minimally privileged path; document and test how it reads/writes embeddings.
4. **Approval workflow:** `memory_approve` creates an idempotent revision-bound review request; it cannot finalize approval. Implement trusted portal-review service methods for approval (who, when, exact revision, note), rejection, and promotion, according to `review-decisions.md`. MCP/PAT bearer calls cannot complete these transitions. Stage 05 supplies explicit browser review. Add archival and authorized scope/member administration CLI/API, including revocation. Lifecycle changes append events rather than modifying historical revisions. Agent-created memories default to `unverified` (or `cited` when a valid `source_uri` is present, per documented rules). Search results always carry trust level and approval info.
4a. **Promotion and override authorization:** enforce the accepted contract in `review-decisions.md` in Go and the database access path. Source-maintainer consent shares only an approved revision snapshot with parent reviewers; destination-maintainer browser acceptance finalizes promotion. Recheck the source revision, submitter's continuing authority, destination authority, and secret scan transactionally. A destination-only maintainer cannot read or supersede arbitrary child memories. Test stale/rejected/revoked requests, idempotency, narrow snapshot visibility, inaccessible provenance redaction, and atomic source/destination changes. Override proposals require write access and an ancestor target; only revision-bound approval activates them, and updating/archiving/superseding the override disables it. Record and test these rules in `docs/decisions/trust-rules.md`; locked organization guidance remains deferred.
5. **Audit log:** append-only `audit_events` (enforced by privileges/triggers) for create, update, supersede, approve, auth failures, and permission denials, with request ID and principal. No memory content in audit payloads beyond identifiers.
5a. **Mirror-readiness (the mirror itself is built in stage 06):** specify in `docs/decisions/mirror-security.md` what may be exported (content, rationale, source_uri, kind, trust, author, approver; never audit events or auth data), that export happens only after secret scanning passes, how mirror repos map to scopes (one repo per scope that owns memories, accessible only to trusted deployment operators and the export worker; users browse history through Team Memory, and no scope-membership-to-git-ACL synchronization is built in v1; inherited memories are not copied into descendant repos), and what happens in the mirror when a memory is archived or must be purged.
6. **Input protection:** request size limits; validation; secret scanning on create/update (detect common credential patterns and reject or quarantine with a clear error); rate limiting per principal. Document limits.
7. **Prompt-injection posture:** retrieved content is returned with explicit untrusted-data framing in tool results and resource text (e.g. structured fields plus a standard preface/metadata marking), and the example agent policy (`docs/agent-policy/AGENTS.md` and `CLAUDE.md` snippets) says to treat memory as data, verify against the repo, and never treat unverified memory as binding. Be honest in docs that this reduces, not eliminates, injection risk.
8. **Adversarial tests** (in `integration/security/`), each as an automated test against real PostgreSQL:
   - Hierarchy attacks: org-only member cannot reach team or project memories by search, get by ID, history, resources, or the portal API; a project member cannot write or approve an org- or team-level memory; a team member cannot read a sibling team's projects; a non-cascading grant never reaches descendants; moving or re-parenting via any API is impossible; a principal removed from a scope loses access immediately (including to cached/pooled state); inherited memories show the right origin and cannot be read at a scope the principal cannot see; deep-tree and many-member cases do not time out or leak.
   - Promotion and override attacks: an agent principal cannot promote; a writer without maintainer on the parent cannot promote; promoting a stale or unapproved revision fails; promotion cannot skip levels; double-submitted promotion is idempotent; an override cannot reference a memory the author cannot see or one in a non-ancestor scope; an override in project A has no effect in sibling project B or at the team; a promoted memory's former content is not readable by anyone newly unauthorized except through the intended wider audience.
   - Principal A in scope X cannot read, search (including vector search), get by guessed ID, list history, or see embeddings/audit of project Y.
   - Reader cannot write; writer cannot approve or supersede.
   - Connection-pool reuse does not leak identity between requests (run interleaved concurrent requests).
   - Missing/unset `app.principal_id` returns nothing.
   - Direct SQL under a fixed request identity as the app role cannot evade visibility policies or modify revisions/audit. Document that the shared app role can set the request-identity variable: RLS does not independently defend against arbitrary SQL execution that impersonates another principal. Test missing identity and connection-pool isolation separately.
   - Wrong-audience, expired, forged, and revoked tokens rejected; a user from a non-allowed email domain or issuer cannot sign in; in facade mode, upstream-IdP tokens are not accepted as Team Memory tokens. If stage 03 selects direct validation, test its explicitly configured issuer/audience contract instead; do not accidentally support an unselected mode.
   - Missing or invalid SSO secret config leaves the server not-ready and unable to serve requests.
   Report any failures honestly; fix them before handoff.

## Excluded
The web portal (stage 05); Helm/production deployment, backups, load testing (stage 06); client verification (stage 07). Third-party penetration testing is outside this prompt; recommend it in the handoff.

## Deliverables
Production auth, RLS migrations, approval workflow, audit log, input defenses, agent policy snippets, adversarial test suite, `docs/decisions/trust-rules.md`, `docs/decisions/mirror-security.md`, `docs/security/threat-model.md` (assets, actors, threats, mitigations, residual risks), `docs/handoff/04-security.md`.

## Acceptance criteria
- Every tenant-owned table has RLS enabled and forced (checked by an automated test that enumerates tables).
- Adversarial suite passes; the cross-tenant and hierarchy tests cover all eight tools and all four resources, and get extended to the portal-facing API once stage 05 builds it.
- `memory_approve` requests review without changing trust. Trusted review services bind approval to an exact revision; MCP/PAT calls, including those using a human maintainer identity, cannot finalize approval or promotion. Tests verify approved versus proposed overrides and promotion consent; browser end-to-end coverage lands in stage 05.
- Audit events exist for each sensitive action and cannot be altered by the app role.
- No unauthenticated mode exists in any configuration (test).
- Threat model lists residual risks, including injection limits.

`docs/handoff/04-security.md`: what is enforced where, test results, residual risks, recommended external review, and config the Helm chart in stage 06 must expose (issuer, audience, DB roles, secrets).
